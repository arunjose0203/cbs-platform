## Environment and method

A fresh PostgreSQL 18.3 instance was initialized under the ignored workspace evidence directory, bound only to `127.0.0.1:55439`, with a generated test credential. After the interruption described below, the deposit retry used a second fresh cluster on loopback port 55440. Each integration fixture created separate temporary control/bank databases and roles. The normal Neon development launcher and its saved database configuration were not used. Tests were scheduled W02 first, then W03, then the full backend verification/package run. UI and operations unit suites were also executed.

The integration suite uses `TestIdentity` signed JWTs and MockMvc/service calls. It checks authorization and MFA claims but does not perform real authenticator enrollment or a browser login to a deployed identity provider. Most core deposit fixtures use INR/India settings; payment/FX fixtures include KES/Kenya. These results must not be presented as acceptance of all three target countries.

The initial sandbox attempt could not initialize PostgreSQL because Windows restricted-token creation failed. The isolated fixture subsequently ran outside the sandbox. This was an environment issue, not a reproduced CBS defect.

The first W03 attempt recorded 27 results with zero assertion failures and six errors after the PostgreSQL parent process exited. Its server log records a Windows shared-memory reservation error (487) before the exit, followed by connection resets/refusals; one error is fixture cleanup. This establishes a database-environment interruption, not a proven financial logic defect or a complete root-cause diagnosis. The interrupted log and XML are retained separately. The retry uses 16 MB shared buffers and 40 maximum connections in a fresh cluster; these are local test settings, not production sizing recommendations.
