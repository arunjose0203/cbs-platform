# Production identity (P-03)

Production-engineering item P-03 (gate E03) of the [go-live plan](go-live-plan-2026-11-13.md). Exit criterion: acceptance case A02 (staff sign-in with MFA, revocation and session expiry) passes on staging.

The development sign-in ([local identity](local-identity.md)) runs Keycloak in dev mode with an H2 database on one workstation. That setup does not move to staging. Staging and production use the setup described here: Keycloak 26 on PostgreSQL behind the same Caddy edge as CBS, with the realm configuration kept in the repository.

## What is in the repository

| File | Purpose |
| --- | --- |
| `config/keycloak/cbs-production-realm.json` | Realm `cbs`: password + OTP on every sign-in, PKCE portal client, a disabled operator service identity. Imported only when the realm does not exist yet. |
| `deploy/staging/compose.yml` (`identity`) | Keycloak with `KC_DB=postgres`, a fixed public hostname, proxy headers from the edge, health and metrics on the management port, and JSON logs. The admin console is published only on `127.0.0.1:8181`. |
| `deploy/staging/Caddyfile` | `IDENTITY_DOMAIN` serves only `/realms/cbs/*` and `/resources/*`. The admin console, master realm, metrics and health return 404 at the edge. |
| `ops/staging_preflight.py` | Rejects an unpinned Keycloak image, a placeholder or shared identity domain, a database URL without `sslmode=verify-full`, a shared database login, leftover placeholders and weakening overrides. Also rejects a CBS runtime that does not trust exactly `https://IDENTITY_DOMAIN/realms/cbs`. |
| `deploy/staging/up.sh` | Starts `identity` with `app` and `edge`. Fails with exit code 5 if the realm discovery document is not reachable over HTTPS. |
| `ops/identity_admin.py` | Signing-key status, rotation and retirement, and staff sign-in account creation, as the operator service identity. Secrets and key material are never printed. |
| `ProductionGuard` | Now also refuses a JWKS URL on a different host from the issuer, and the `cbs-dev` realm. |
| `MigrationMain` (`firstAdministrator`) | Registers the first CBS staff record for an identity provider, offline and audited, because production forbids the runtime bootstrap subject. |

## Realm controls

- **TLS everywhere** (`sslRequired: all`). No self-registration, password reset by email, remember-me, username edits or email login.
- **Every browser sign-in** runs the `cbs-password-and-otp` flow: password, then OTP, both required, with no cookie-only path. New accounts must enroll OTP (`CONFIGURE_TOTP` is a default required action). OTP codes cannot be reused.
- **MFA evidence.** The `amr` claim gets `pwd` and `mfa` from the completed steps, valid for 30 minutes. This matches CBS's administrator MFA window (`administratorMfaAge`).
- **Passwords:** at least 14 characters with mixed classes and a special character, not the username or email, and no reuse of the last 12. Brute-force protection: 5 failures, then a wait that grows to 15 minutes.
- **Lifetimes:** 15-minute access tokens, 15-minute SSO idle time, 8-hour maximum session, all within CBS's own limits. The portal keeps tokens in memory only and does not use refresh tokens. When a token expires, the user signs in again.
- **Portal client `cbs-portal`:** a public client with S256 PKCE. Its only redirect URI is `https://CBS_DOMAIN/admin/index.html`, its only web origin is `https://CBS_DOMAIN`, and it has no wildcards. Direct, implicit, device and CIBA grants are off. Tokens carry the `cbs-api` audience, realm `roles` (only `PLATFORM_ADMIN` is in scope) and `amr`. The mappers are the same as the development realm's (checked by `ops/tests/test_identity_realm.py`).
- **Bank duties are not Keycloak roles.** Maker, checker, teller, credit, collections, finance and auditor duties are granted inside CBS (Staff & Access, bank duties, lending access). Keycloak only proves who the person is.
- **Events.** Login and admin events are kept for 90 days. Admin event details are off, so representations containing credentials are not stored. Successful logins are logged at INFO, in JSON, for log aggregation (P-05).
- **Service identity `cbs-identity-operator`:** confidential, client-credentials only, 2-minute tokens. It holds `view-realm`, `manage-realm`, `view-users` and `manage-users` in `realm-management`, not `realm-admin`. It is **disabled** in the template: enable it for an operations window, then disable it again. Its secret is generated by Keycloak and never stored in the repository.
- **Signing keys** are generated by Keycloak (RS256, 3072-bit on rotation). The template ships no key material.

CBS's batch scheduler (P-07) uses a configured CBS staff identity, not a Keycloak service account. CBS rejects tokens without `sid` and `auth_time`, so client-credentials tokens cannot call the CBS API.

## Installing on the staging host

1. **Database.** As DBA, create a separate login and database for Keycloak on the PostgreSQL server (or a separate server):
   `CREATE ROLE cbs_identity LOGIN PASSWORD '<from secret store>'; CREATE DATABASE cbs_identity OWNER cbs_identity;`
   Keycloak manages its own schema. Do not reuse the CBS control, bank or migration logins, which preflight checks. Add `cbs_identity` to the backup inventory (see [production deployment and recovery](production-deployment-recovery.md); P-04 adds PITR).
2. **DNS.** Point `IDENTITY_DOMAIN` (for example `id.bank.co.ke`) at the host. It must differ from `CBS_DOMAIN`, so the sign-in pages and the portal keep separate browser origins. Caddy obtains both certificates.
3. **Private identity environment file**, for example `/etc/cbs/identity.env`, mode 600, root-owned:
   ```
   KC_DB_URL=jdbc:postgresql://DB_HOST:5432/cbs_identity?sslmode=verify-full&sslrootcert=/opt/keycloak/conf/db-ca.crt
   KC_DB_USERNAME=cbs_identity
   KC_DB_PASSWORD=<from secret store>
   KC_BOOTSTRAP_ADMIN_USERNAME=bootstrap-admin       # first start only
   KC_BOOTSTRAP_ADMIN_PASSWORD=<one-time, from secret store>
   ```
   The database CA is the same file as `CBS_DATABASE_CA`. Preflight refuses `KC_HOSTNAME_STRICT`, `KC_FEATURES`, `KC_DB_URL_PROPERTIES` and similar overrides. Change the reviewed configuration in the repository instead.
4. **Staging env file** (`/etc/cbs/staging.env`): add `KEYCLOAK_IMAGE=quay.io/keycloak/keycloak@sha256:<digest of the reviewed 26.x release>`, `IDENTITY_DOMAIN=…` and `CBS_IDENTITY_ENV=/etc/cbs/identity.env`.
5. **CBS runtime file:** `cbs.security.issuer: https://IDENTITY_DOMAIN/realms/cbs`, `jwk-set-uri: https://IDENTITY_DOMAIN/realms/cbs/protocol/openid-connect/certs`, `audience: cbs-api`, `cbs.portal.client-id: cbs-portal`, `redirect-uri: https://CBS_DOMAIN/admin/index.html`. Preflight checks every one of these values.
6. Run `deploy/staging/up.sh --env-file /etc/cbs/staging.env`. On first start, Keycloak creates its schema and imports the `cbs` realm with `CBS_DOMAIN` substituted.

## First administrator and the bootstrap account

The bootstrap account lives in the `master` realm and is temporary.

1. Open an SSH tunnel: `ssh -L 8181:127.0.0.1:8181 <host>`. Then browse to `http://127.0.0.1:8181/admin/` and sign in with the bootstrap account.
2. In `master`, create a named permanent administrator, give it the `admin` role and require OTP for it. Sign in as that user with OTP, then delete the bootstrap user.
3. Remove `KC_BOOTSTRAP_ADMIN_*` from the identity env file and restart the `identity` service.
4. Rotate the `cbs-identity-operator` client secret (Clients → Credentials → Regenerate), store it in the secret store, and leave the client disabled.

### First CBS platform administrator

The production guard forbids the runtime bootstrap subject (`cbs.access.bootstrap-admin-subject`). The first CBS staff record is registered by the offline migration job instead.

1. Create the person's sign-in account with `create-staff` (below) and give them the `PLATFORM_ADMIN` realm role in the admin console (Users → Role mapping).
2. Add to the private migration `plan.json`:
   ```json
   "firstAdministrator": {"issuer": "https://IDENTITY_DOMAIN/realms/cbs", "subject": "<subject from create-staff>",
                          "displayName": "Jane Otieno", "email": "j.otieno@bank.co.ke"}
   ```
3. Run the migration job (`up.sh` does this). It prints `First administrator: REGISTERED` and writes a `FIRST_ADMIN_REGISTERED` identity audit entry with actor `system:migration-job`.

The job applies this only while **no staff exist for that issuer**. Re-runs report `CURRENT`. Any other subject for the same issuer is refused, so later administrators and staff are registered through the portal. Placeholders and non-HTTPS issuers are refused. The same step registers the first administrator after a switch to another identity provider, because that is a new issuer.

## Staff sign-in accounts (Phase 0.4)

Enable `cbs-identity-operator`, then:

```sh
python3 ops/identity_admin.py --secret-file /etc/cbs/identity-operator.secret create-staff \
    --username j.otieno --first-name Jane --last-name Otieno --email j.otieno@bank.co.ke \
    --password-out /root/handover/j.otieno.first-login
```

The account must change its temporary password and enroll OTP at first sign-in. The temporary password is written only to the new private file (mode 600, never overwritten). The output gives the Keycloak subject. Register that subject as CBS staff and grant duties in CBS. Hand over the password file through a separate channel. Create distinct maker, checker, teller, credit, collections, finance and auditor identities; CBS enforces that a maker never approves their own request.

To remove access, disable the CBS staff record. CBS rejects the person's existing tokens and sessions immediately (`STAFF_DISABLED`, `SESSION_REVOKED`). Disable the Keycloak user as well.

## Signing-key rotation

Keycloak signs tokens with the highest-priority active key. Passive keys stay in the JWKS, so tokens already issued keep validating. CBS caches the JWKS for about 5 minutes.

```sh
python3 ops/identity_admin.py --secret-file … keys                        # kid, status, priority; no key material
python3 ops/identity_admin.py --secret-file … rotate                      # new RS256 key above all others; old keys become passive
python3 ops/identity_admin.py --secret-file … retire --grace-minutes 60   # after the grace, disable passive keys
```

`rotate` creates the new key before it demotes the old ones, so there is never a moment without a signer. `retire` refuses to run until the newest rotation is older than the grace period. It also refuses grace periods under 45 minutes, which covers 15-minute tokens plus JWKS caching. Delete disabled providers in the admin console after the next backup. Rotate on a schedule agreed with the bank (suggested: quarterly), and at once if key exposure is suspected. In that case, retire after the grace and revoke sessions (Realm → Sessions → Sign out all) to force fresh sign-ins.

## Recovery

Back up the `cbs_identity` database with the CBS databases. A restore of CBS without the matching identity database makes registered subjects unknown to the identity provider. Back up the identity env file and the operator secret through the secret store. The realm file in the repository recreates the configuration but not users, OTP enrollments or keys. If identity is lost, all staff must be re-created and re-registered.

## Using the bank's own identity provider instead

If the bank requires its own IdP (Entra ID, an existing Keycloak, Okta), CBS needs the same claims: an exact HTTPS issuer, a JWKS URL on the issuer's host, the `cbs-api` audience, `sid`, `auth_time`, `amr` containing `mfa` when OTP or an equivalent passed, and `roles` containing `PLATFORM_ADMIN` for platform administrators. Federating that IdP into this realm (Identity providers → OpenID Connect) keeps these claims stable, and is the recommended route.

## Verification (14 November 2026)

- **Real Keycloak 26.7.4.** `cbs-production-realm.json` was imported into a throwaway Keycloak with an in-memory database on loopback. The following were then checked through the admin API:

  - `CBS_DOMAIN` substitution in the portal URIs, S256 PKCE and the three claim mappers

  - `CONFIGURE_TOTP` is a default action
  - the operator client is disabled after import, and a disabled client gets no token
- **The operator tool against that Keycloak:**
  - `keys` lists no key material
  - `rotate` made the new key the signer and left the old key passive, and both stayed in the JWKS
  - `retire` was refused inside the grace period
  - `create-staff` set `UPDATE_PASSWORD` and `CONFIGURE_TOTP`, never printed the password and refused a duplicate
  - the operator token got 403 on the master realm and on client configuration, and could see only the `cbs` realm
  - no secret appeared in any output
- **Not run here:** Docker is not installed on this PC, so `docker compose config` with the new service runs in CI. The `up.sh` tests are POSIX-only: they run in CI, and the new paths (realm unreachable → exit 5, full order) were also exercised by hand in Git Bash with stub commands.
